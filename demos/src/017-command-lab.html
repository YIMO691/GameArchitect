Lesson 017: commands for input, undo and replays

      
    
    
    
  
    

  
    
    
    What this shows
    
    
    
      
    Input once, at one door
    A button that is "down" for one frame is seen 0 times by a fixed step on a 120 Hz screen and 2 times on a 30 fps phone. A command stamped with its tick runs exactly once.
    
      
    Undo stores the change
    A snapshot copies the whole reef: 5.76 MB per step, 576 MB for 100. A command keeps only what it changed: 0.53 MB. It must name objects by stable ID, or Undo moves a deleted rock.
    
      
    Replay needs determinism
    Commands and a seed are 24.1 KB for 10 minutes instead of 3.9 GB. But one shared random or one clock read makes the replay drift. Checksums show when; snapshots make seeking fast.
    
    
    
    
    Input and undo memory are a simulation using Lesson 017's numbers: a 60 Hz fixed step; 48 B per reef object; 120,000 objects (5.76 MB) per snapshot; command sizes 64 B (rock), 1,936 B (brush of 40), 36 B (move), 16 B + 48 B per removed object (clear: 2,000 objects per patch). The undo stack, the editor and the rock bug are real code running here. The replay is a real deterministic mini simulation (16 fish, one hook, 1,200 ticks = 20 s, 12 commands) recorded as if on a 30 fps phone and replayed in fast-forward; its mismatches are produced live, not scripted. The 10-minute sizes (24.1 KB, 3.9 GB, 2.2 MB) and seek times (2.11 ms per tick: 66.6 s and 2.0 s) come from the lesson and are approximate. A real engine has more sources of non-determinism, such as floating-point differences between CPUs and job order.
