The harbour in a commercial engine runs at 22 ms. A frame passes through the game thread, the worker threads, the render thread and the GPU, each working on a different frame at the same time. Change the work on each stage and see which one sets the frame time, and how long a button press takes to reach the screen.

One capture, four stages. Goal: 60 fps (16.7 ms or less) and 40 ms or less from input to the frame being finished, without lowering the resolution.

Lesson 075: a commercial engine runtime

    What this shows

    Stages overlap

    While the GPU draws frame N, the render thread prepares N+1 and the game thread simulates N+2. The frame time is the slowest stage, not the sum.

    Find the slowest stage first

    Making a stage that isn't the bottleneck faster changes nothing. Lowering resolution on a game-thread-bound frame is wasted quality.

    Latency is the sum

    Pipelining buys throughput, not responsiveness: an input still passes through every stage. Shorter stages help both.

    This lab is a model, not a measurement. It uses Lesson 075's numbers for one harbour frame on a mid-range PC: game thread 22 ms (9 ms of it ticking 1,600 actors that don't need it, 3 ms of animation), render thread 12 ms, GPU 14 ms at native resolution or 9 ms at 75% scale. Worker threads take the animation in parallel. Pipelined, the frame time is the slowest stage; one after another, it's the sum. Input to finished frame is the sum of the stages either way; real engines add display and queueing time on top.
